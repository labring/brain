# GitHub OAuth "disconnect" semantics and GitHub account switching across developer platforms

Research date: 2026-07-23. Investigated against primary sources only (GitHub's own docs, vendor first-party docs, and vendor-owned support/community threads). Where a claim could only be reached through a third-party blog, or where no first-party statement exists, this is called out explicitly as **no primary evidence found**.

A recurring caveat: most vendors expose a **repo-level "disconnect"** (detach a repository from a project) and a separate, less-visible **account/integration-level disconnect**. The research question is about the latter (the OAuth authorization), so the two are distinguished per vendor below.

---

## TL;DR

**1. Disconnect semantics (does the vendor revoke on GitHub's side?).** No vendor examined **publicly documents** calling GitHub's `DELETE /applications/{client_id}/token` or `.../grant` when you press "disconnect." The observed pattern is overwhelmingly **local-forget**: the product deletes its own connection record and, where a real GitHub-side revoke is wanted, **points the user at GitHub's own settings** (`github.com/settings/connections/applications/…` for OAuth Apps, `github.com/settings/installations` for GitHub Apps). The one clear exception in first-party docs is **Supabase**, which states that its account-level "Remove connection" **"revokes the OAuth grant entirely,"** while its org-level delete **"does not revoke the underlying OAuth grant on the account level."** ([Supabase](https://supabase.com/docs/guides/troubleshooting/managing-or-disconnecting-github-oauth-connections-e3dc3b)) Strong indirect local-forget evidence comes from Fly.io (a user revoked Fly's OAuth grant on GitHub yet **could still sign in** to Fly via GitHub — the identity link is stored locally, independent of the token) ([Fly community](https://community.fly.io/t/fully-disconnect-github-from-account/13297)) and from Vercel (users get **locked out of Vercel** after revoking Vercel on GitHub's authorized-apps page, i.e. Vercel treats the GitHub grant as a live login dependency rather than something it cleans up itself) ([Vercel community](https://community.vercel.com/t/pro-account-locked-out-after-revoking-vercel-from-github-authorized-apps/38811)).

**2. Account switching.** No vendor ships a first-class "switch GitHub account" button. The universally-suggested workaround is **"sign out of GitHub first, then reconnect/sign up again"** — stated verbatim by Vercel ([Vercel docs](https://vercel.com/docs/git/vercel-for-github)). GitHub itself is the only place with a real mechanism, and it is now documented: the `authorize` URL supports **`login`** ("Suggests a specific account to use for signing in and authorizing the app") and, more importantly, **`prompt=select_account`**, which **"Forces the account picker to appear."** The picker **also** appears automatically "if the application has a non-HTTP redirect URI or if the user has multiple accounts signed in." ([GitHub docs](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)) `login` alone only *suggests*; `prompt=select_account` is the reliable force. No primary evidence found that any of these vendors actually pass `prompt=select_account`.

**3. GitHub lifecycle facts.** `DELETE /applications/{client_id}/grant` **"will also delete all OAuth tokens associated with the application for the user"** and de-lists the app from the user's authorizations screen; `DELETE .../token` revokes only **"a single token."** Both require **Basic auth with `client_id` as username and `client_secret` as password**, and take the `access_token` in the body. ([GitHub docs](https://docs.github.com/en/rest/apps/oauth-applications)) A user revoking the app from their own account settings does the equivalent of grant-deletion: **"which will revoke any tokens associated with the app."** ([GitHub docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)) OAuth App tokens **do not carry an expiry** but are auto-revoked after **one year of non-use**; there is a limit of **ten tokens per user/application/scope** (oldest rolled off beyond that). GitHub *App* user-to-server tokens are different: they **expire after 8 hours** with a refresh token.

**App-type migration note.** The GitHub-App-vs-OAuth-App split matters because grant semantics differ. Vercel, Netlify (new sites), Render, Railway, Sentry, and CircleCI (new) all use **GitHub Apps** for repository access — often *alongside* an OAuth flow used purely for login. Heroku (github.com) and Supabase remain **OAuth Apps**. For a GitHub *App*, "the grant" that a user revokes is the **installation** (repo access) and, separately, the per-user user-to-server **authorization**; for an OAuth *App*, the grant is the single per-user×app authorization that this research is centered on.

## GitHub API / lifecycle facts (primary source: GitHub Docs)

### The two revoke endpoints
Both live under "REST API endpoints for OAuth authorizations" and work for **both** OAuth App tokens (`gho_` prefix) and GitHub App user tokens (`ghu_` prefix). ([oauth-applications](https://docs.github.com/en/rest/apps/oauth-applications))

- **`DELETE /applications/{client_id}/grant`** — "Delete an app authorization." Verbatim: *"Deleting an application's grant will also delete all OAuth tokens associated with the application for the user. Once deleted, the application will have no access to the user's account and will no longer be listed on the application authorizations settings screen within GitHub."* Input: a valid `access_token` in the body; the grant of **that token's owner** is deleted. Returns `204`.
- **`DELETE /applications/{client_id}/token`** — "Delete an app token." Verbatim: revokes *"a single token for an OAuth application or a GitHub application with an OAuth authorization."* Other tokens for the same user×app survive. Returns `204`.
- **`POST /applications/{client_id}/token`** — "Check a token" (validate without burning the failed-login rate limit). **`PATCH .../token`** — "Reset a token" (issues a new token string, old one invalidated immediately).

### Auth for these endpoints
Verbatim for both delete endpoints: *"You must use Basic Authentication to use this endpoint. Use the application's `client_id` as the username and the `client_secret` as the password."* These are **app-owner** (server-to-server) endpoints — you do **not** use the user's token as the credential; you pass it in the body. ([oauth-applications](https://docs.github.com/en/rest/apps/oauth-applications))

### Does the user get notified? / user-initiated revoke
- A user revoking from their own settings is equivalent to grant-deletion: *"You can revoke your authorization of a GitHub App or OAuth app from your account settings which will revoke any tokens associated with the app… Once an authorization is revoked, any tokens associated with the authorization will be revoked as well."* ([token-expiration-and-revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation))
- No primary evidence found that GitHub sends the user a notification specifically when an **app owner** calls the grant/token delete API (as opposed to the user acting themselves). Treat "user is notified" as **unconfirmed**.

### Token expiry & the per-fingerprint limit (OAuth Apps)
From "Authorizing OAuth apps" and "Token expiration and revocation":
- OAuth App tokens have **no intrinsic expiry**, but GitHub *"will automatically revoke an OAuth token or personal access token when the token hasn't been used in one year."*
- *"There is a limit of ten tokens that are issued per user/application/scope combination, and a rate limit of ten tokens created per hour. If an application creates more than ten tokens for the same user and the same scopes, the oldest tokens with the same user/application/scope combination are revoked."* So the fingerprint is **user × app × scope-set** (10 max).
- Other automatic revoke triggers listed: token pushed to a public repo/gist; revoked by a third party; revoked by the OAuth app; revoked due to excess tokens; revoked by enterprise owners.
- Re-authorizing an already-authorized OAuth app **skips the scopes screen**: *"the user won't be shown the OAuth authorization page with the list of scopes. Instead, this step of the flow will automatically complete with the set of scopes the user has authorized."* (Implication: re-running the flow won't re-prompt consent, which is why an account switch needs `prompt=select_account`, not just a re-auth.)

Sources: [authorizing-oauth-apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps); [token-expiration-and-revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation).

### GitHub App user tokens differ
GitHub App user-to-server tokens **expire after 8 hours by default**, refreshable via a refresh token (refresh token valid ~6 months). ([generating-a-user-access-token-for-a-github-app](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app))

### Authorize-URL parameters relevant to account switching
From the OAuth authorize parameter table ([authorizing-oauth-apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)):
- **`login`** (optional) — *"Suggests a specific account to use for signing in and authorizing the app."* This only *suggests*; if the user's active GitHub session is a different account and the app is already authorized, GitHub can silently complete with the current session. It is **not** a forced switch.
- **`prompt`** (optional) — *"Forces the account picker to appear if set to `select_account`. The account picker will also appear if the application has a non-HTTP redirect URI or if the user has multiple accounts signed in."* This is the reliable "let me pick/switch accounts" lever.
- Other params: `client_id` (required), `redirect_uri`, `scope`, `state`, `code_challenge` / `code_challenge_method` (PKCE, S256 only), `allow_signup`.
- Redirecting through `https://github.com/logout` first is **not documented by GitHub** as a supported switch mechanism (**no primary evidence found**); `prompt=select_account` is the documented equivalent.

## Implications for a per-(namespace, user) connection product

Context recap: we store one OAuth token per `(namespace, user)`, but a GitHub **grant is per GitHub-account × app**. This is exactly the Supabase hazard, made concrete by GitHub's own wording.

1. **Never call `DELETE /applications/{client_id}/grant` from a single workspace's "disconnect."** GitHub is explicit that grant-deletion *"will also delete all OAuth tokens associated with the application for the user"* — so one namespace disconnecting would silently kill the tokens every **other** namespace of the same GitHub user holds. This is the core failure mode to avoid.
2. **A "disconnect" button should default to local-forget** (delete our `(namespace, user)` token row and stop using it) — the same thing Vercel/Fly/Railway effectively do. This is the safe, blast-radius-free default and matches how the ecosystem behaves.
3. **If you want a real GitHub-side revoke, use `DELETE .../token` (single token), never `.../grant`.** Token-delete revokes only the one token you hand it, leaving other namespaces' tokens intact. Caveat: because GitHub fingerprints tokens by **user × app × scope**, if all your namespaces request the **same scopes**, GitHub may itself collapse them toward the 10-token limit — so don't assume "one token per namespace" is guaranteed durable at GitHub; keep tokens usable and consider distinct handling if you exceed ~10 concurrent tokens for one user.
4. **Offer an explicit, separate "revoke on GitHub" affordance** that either (a) deep-links the user to `github.com/settings/connections/applications/{client_id}` (OAuth App) and lets them decide, or (b) calls token-delete for *only the current namespace's* token. Reserve grant-deletion for a deliberate "remove GitHub from my entire account everywhere" action, clearly labeled as global.
5. **Account switching:** don't rely on `login` alone (it only *suggests*). Send users through the authorize URL with **`prompt=select_account`** to force GitHub's account picker; this is the only GitHub-documented way to let a signed-in user pick a different account without logging out. As a fallback, mirror Vercel's guidance ("sign out of GitHub first, then reconnect"). Because re-authorizing an already-authorized app **skips the consent screen**, `prompt=select_account` is what actually makes the switch visible to the user.
6. **Because our token per namespace is independent, "switching accounts" should be modeled as: acquire a new token (via `prompt=select_account`) and overwrite only the current `(namespace, user)` row** — do not revoke the old grant, since it may still back other namespaces.
