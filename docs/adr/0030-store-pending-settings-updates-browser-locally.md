# Store Pending Settings Updates Browser-Locally

An accepted-but-not-yet-reconciled Settings target is remembered in the user's browser local storage — not in backend Project state, not in provider-local React state. Local storage survives closing settings, entering the same Settings Owner through another Settings View, and browser refresh, without making a private in-flight target shared Project truth. In-flight and rejected submissions never enter this storage; they stay in the settings submission layer for the current session only. A backend settings-operation model is the exit if cross-user visibility, audit, or durable failure handling becomes necessary.

## Rules

- **Storage key**: cluster fingerprint + Settings Owner kind + namespace + name + observed resource UID when available + Settings Domain. The fingerprint must never store raw kubeconfig material. If a later observed UID does not match the one stored for the same kind, namespace, and name, ignore that stale target rather than applying it to a recreated resource.
- **The stored value is the canonical target for one Settings Domain, not the API patch that submitted it.** Patches are write commands; a pending target has to support display overlays and domain-level reconciliation against observed state. For AP Environment the target is the AP Environment Raw Source — compiled runtime rows are write output, usable only as a fallback projection when a resource has no observed Raw Source.
- **Observed Settings Divergence**: each pending target also records the observed domain target it was submitted against. If observed desired configuration later equals neither that value nor the pending target, a third party changed the resource — ask the user to Keep Target or Use Latest. Never silently drop the pending target, never silently overlay it onto the changed resource. Submit-time conflict detection is pending-aware for the same reason: observed state still equal to the submitted-against target means the resource has not caught up, not that a conflict exists.
- **No Retry action.** The stored value is not the original write command, so resubmission goes through the normal Settings Draft submit flow and rebuilds any patch against current observed backing. Attention-needed targets offer Edit and Use Latest only, and Use Latest must not bypass unsaved-change protection — resolve the existing discard confirmation first.
- **Lifecycle**: a pending target is created only for the Settings Domains that were dirty in the submitted draft, and is cleared when observed desired configuration matches it, when the user abandons it, or when a newer submission replaces it. Reconciliation compares desired configuration only — never runtime readiness, rollout completion, routing health, certificates, DNS verification, or storage expansion. Past the attention window a target becomes attention-needed: never silently deleted, and never inferred failed from time alone.
