# Pin Chat Context to Each User Message

The Project Assistant previously rebuilt a workspace block from the *current* project and canvas selection on every request and prepended it to the system prompt, ahead of the full replayed history. Because the block always described "now", a past turn's deictic reference ("deploy this", "scale it") was re-read against whatever happened to be selected on the later request: select service A and say "deploy this", then select B and ask a follow-up, and the model resolves the first "this" to B — A's identity was never stored anywhere. The same volatile block sat at the top of the system prompt, so each selection change invalidated the provider's cached prefix (OpenAI prompt caching is exact-prefix), and the client-supplied resource name rode inside the highest-authority part of the prompt. We now snapshot the selected resource when a user message is sent and pin it to *that* message as a `data-selectedResource` part; the model sees it, per turn, as a delimited `<selected_resource>` block injected at convert time, and the system prompt carries only thread-stable project context.

## Considered Options

- Keep the selection in the system prompt but recompute it per request (the previous shape): rejected — it structurally cannot preserve a past turn's referent, and a volatile prefix defeats prompt caching for the whole system prompt plus tool schema on every selection change.
- Pin the selection but only re-emit it when it changes (snapshot-on-change): rejected as the primary rule — a follow-up about an unchanged selection then carries no referent of its own and dangles if history is later truncated or summarized. We re-snapshot the ambient selection on every send (matching Cursor/Copilot's implicit-context model) so each turn is self-contained, and only *de-duplicate at convert time*: a run of identical consecutive selections renders the full block once, then a terse "unchanged" marker. This is safe because the full thread is always replayed from storage; if wire-level truncation is ever added, the de-dup must re-expand at the truncation boundary.
- Store the context in message `metadata` instead of a data part: rejected — `convertToModelMessages` drops `metadata` entirely, so it never reaches the model without a bespoke bridge, and it is awkward to render as a UI affordance later. A `data-*` part persists in `message.parts`, survives reload, and has a supported model bridge (`convertDataPart`, or the pre-pass used here).
- Pass the selection as a tool argument only (no conversational context): rejected as insufficient — the model needs the referent to resolve "this"/"it" in ordinary discussion, not just when a tool fires. The deploy tool still takes structured target arguments; the pinned block is additive.
- Backfill a stale selection when nothing is selected: rejected — absence of a selection is recorded as absence (no block injected), and the reference falls back to conversation memory, which matches user intent when they clear the selection but keep talking about a named resource.

## Consequences

- The canvas selection is captured at send time (kind, name, and namespace) and pinned to the user message as a `data-selectedResource` part. It persists with the message and is replayed on every later request, so "this"/"it" always resolves to the selection that was live when the message was sent.
- The snapshot deliberately carries only `kind`, `name`, and `namespace` — the fields the model reasons with and that the chat tools target by. The Kubernetes `uid` is intentionally omitted: no chat tool consumes it (product reads and writes address resources by kind + name + namespace), and within a namespace `kind + name` already identifies the resource, so a uid would be opaque noise in the block. (An earlier draft declared a `uid` field but it was never populated — the selection is reconstructed from the URL, which does not encode the uid — so it was removed rather than wired through.)
- The system prompt workspace block carries only thread-stable values (authoritative namespace + Brain project name/id). It is a byte-stable, cacheable prefix; the volatile selection no longer sits in it.
- The model receives the selection as a `<selected_resource … />` block prepended to the user turn at convert time, labeled as data (not instructions). Resource names are attribute-escaped, so a crafted name cannot break out of the block, and untrusted input no longer enters the system prompt.
- A turn sent with nothing selected injects no block. Consecutive identical selections collapse to an "unchanged" marker to avoid re-sending the full block every turn.
- The project name sent to the model is now the human-readable display name (previously the project id was sent mislabeled as the display name).
- The transcript renderer ignores unknown parts, so the pinned part is invisible in the UI for now; rendering it as a per-message context pill (Copilot-style "references used") is a deferred follow-up.
- The pinned part is stored verbatim by the existing message persistence, giving an audit trail of exactly which resource was selected when each message — including a deploy request — was sent.
