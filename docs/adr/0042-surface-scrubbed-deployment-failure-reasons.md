# Surface Deployment Failure Reasons Behind a Per-Runner Scrub Gate

A failed Deployment Task must present the real provider/Kubernetes error as ground truth in the Deployment Task Timeline, not collapse to a generic "Deployment task failed." The failed Deployment Timeline Step's inline Deployment Failure Reason follows a three-tier precedence — a recognized failure-class headline when one applies, else the first line of the ground-truth error, and the generic string only when neither a reason nor any error text exists — while the full Deployment Failure Detail is available under the failed step in an expandable, copyable disclosure. The raw error already reaches the client on `task.error` / `task.failureDetails`, so no field is added to the timeline-event model.

Because a displayed error can echo submitted input values, the ADR 0037 row-level secrets contract is extended to cover failure and error strings: every persisted copy of a terminal failure (event message, `payload.error`, `failureDetails`) is scrubbed of known sensitive values — raw, JSON-escaped, and base64 forms, via the same scrub used for rendered YAML — at the single terminal failure write, before persistence. Read-time DTO redaction remains defense-in-depth, not the guarantee. Only the runner holds the plaintext sensitive values in memory, so the scrub is runner-local in effect: the runner attaches its known sensitive-value set to the thrown error and the terminal write scrubs with it. Displaying the raw error and scrubbing it are the same decision — **a runner surfaces its raw error only if that runner's terminal error is scrubbed** ("scrub ⇔ raw display").

Template and direct runners pass the gate now: their sensitive values are a structured, enumerable set (template args / settings values), so both enable the raw error and the raw-first-line fallback. The AI Runner does not — the Codex Gateway can echo arbitrary secrets it read or generated, for which no known-value set exists — so it keeps curated messages plus the generic fallback (no raw-first-line) until its terminal error string goes through a key-name/token redaction like the one already applied to its persisted gateway snapshot. All runners still get the shared spine: engine-verdict headlines, the copy affordance, and a rendered Deployment Failure Detail.

## Considered Options

- Curated failure vocabulary only (extend the failure summary per runner, keep hiding the raw error): rejected — the provider/Kubernetes error space is a long tail that will never be fully mapped, so unmapped failures stay opaque. This is exactly why templates fell to the generic string.
- Show the raw error everywhere with no scrub: rejected — the terminal error is persisted in Postgres and can echo submitted secrets, violating the ADR 0037 no-secrets-at-rest posture (a gap that already exists latently for the unscrubbed error string today).
- Scrub at read time in the DTO only: rejected — write-time scrubbing is the guarantee under ADR 0037; a persisted plaintext secret is the exposure, independent of any single reader.
- A stronger scrub over arbitrary error text (regex secret detection): rejected — inconsistent with the rest of the system and a false-confidence rabbit hole. The guarantee matches the YAML scrub exactly — known declared/heuristic sensitive values — no weaker and no stronger.

## Consequences

The terminal failure write becomes the scrub chokepoint; each runner opts into raw-error display by attaching its known sensitive-value set. The failure-summary logic gains the three-tier precedence and a small seed set of headlines: reason-code verdicts (the runner-attached `readiness-timeout`) and the curated AI messages apply to every runner as fixed labels, while the substring-matched template classes (quota-exceeded, name-conflict, invalid-input, provider-unreachable) and the raw-first-line fallback apply **only** to runners that surface the raw error — a false-positive substring must never label a runner that has no raw error to correct it. The template runner's previously silent `template_declarations_unavailable` degrade becomes a warning-severity event on the prepare step. The AI Runner's raw-error display is tracked separately.

Scope of the scrub in this change is the single terminal failure write, which covers the real echo risk (the provider/Kubernetes apply error). Error strings written outside it — the non-terminal `input_rejected` re-park, the engine's own crash-fallback resolution, and the pre-`try` throw sites (instance-name allocation, direct settings validation) — are not yet scrubbed; they are our own messages or carry no run secrets, and full coverage is a follow-up rather than part of this contract. Engine-resolved verdicts (interrupted, timeout, cancelled) keep the reaper's descriptive wording until the reaper marks the timeline through the same reason resolver. CONTEXT.md gains Deployment Failure Reason and Deployment Failure Detail.
