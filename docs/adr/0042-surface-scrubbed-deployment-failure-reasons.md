# Surface Deployment Failure Reasons Behind a Per-Runner Scrub Gate

A failed Deployment Task must present an actionable Deployment Failure Reason in its failed Deployment Timeline Step rather than collapse to a generic "Deployment task failed." The reason has a stable machine-readable code and a curated user message. Deterministic direct/template runners may additionally expose their scrubbed provider/Kubernetes error as the Deployment Failure Detail. The AI runner instead exposes only allowlisted technical context — reason code, task phase, optional upstream HTTP status, and Task ID — because its raw Gateway and command errors can contain arbitrary repository or generated secrets. The existing `failureDetails` JSON and event payload carry the classification, so no database field or migration is required.

Under ADR 0037, generated inline Sealos Template source is retained byte-for-byte as executable Sealos DSL; it is not parsed, serialized, redacted, or normalized before expression rendering. Failure and error strings are separate operational records and can echo request credentials or unrelated provider data. For direct/template runners, every persisted copy of a terminal failure (event message, `payload.error`, `failureDetails`) is scrubbed of known sensitive values — raw, JSON-escaped, and base64 forms — at the terminal failure write. The runner attaches its known sensitive-value set to the thrown error so the terminal write can scrub it. This text scrub is for display and audit copies; it must not be applied to the retained template source, whose scalar, collection, and Sealos expression semantics must remain executable. Displaying the raw error and scrubbing it are the same decision — **a runner surfaces its raw error only if that runner's terminal error is scrubbed** ("scrub ⇔ raw display").

Template and direct runners pass the raw-display gate because their sensitive values are a structured, enumerable set (template args / settings values), so both enable the scrubbed raw error and raw-first-line fallback. The AI runner does not: its terminal write replaces the raw error with the curated message, persists only allowlisted structured failure details, and omits `payload.error`. Raw Gateway SSE payloads become empty invalidation signals instead of being forwarded to the browser; persisted Gateway state contains only lifecycle booleans and validated timestamps, while the URL/session capability and Devbox locator remain internal to the authenticated proxy route. Transcript text is not copied into Deployment Task messages. Read-time DTO projection reconstructs AI event kind/message and Timeline step/card/event fields from fixed catalogs, removes raw AI errors and provider status from legacy rows, hides Gateway/runtime locators, and omits generated `buildResult` as defense in depth. Sealos Template input declarations produced by the current runner are trusted deployment metadata. The artifact projection version attests both the persisted plan and the Blocking Inputs derived from that plan by the same runner; Timeline result cards retain their independent projection version. Unversioned legacy AI inputs fail closed and require Redeploy. The input action accepts only the canonical key published for each AI blocker; an internal blocker ID is not a second submission protocol. The generated Sealos Template DSL and all generated configuration are persisted unchanged as task deployment configuration, but are not copied into Timeline events, failure details, or Gateway transcripts. No sensitivity or content inference is performed over AI output; `secret` and `password` only control UI masking. Submitted Blocking Input values and rendered Kubernetes YAML remain request-memory-only. Client-owned AI Canvas projection fields are never returned as trusted deployment output. Chat status reads use that same safe task/event projection together with the task-owned Deployment Task Timeline and never use runner messages as a transcript or progress fallback. Unknown AI failures still expose the `unknown` code and Task ID with a support instruction.

The stable AI failure vocabulary covers GitHub authentication, repository clone, AI Proxy credentials, deploy/build runtime, skill installation, BuildKit startup and image-build failure, Gateway exposure/availability/5xx/timeout, missing deployment output, Apply/quota/readiness, interruption, maximum duration, never-started tasks, runner crashes, cancellation, and unknown failures. Integration boundaries attach the narrowest reason they can prove; Gateway failures retain only a validated HTTP status. Engine reaping uses the same vocabulary, and read-time timeline projection overlays a deterministic failed step for engine-resolved failures without incrementing the persisted timeline revision.

A failure reason does not introduce another waiting state. `blocked` retains its ADR 0037 meaning: the current attempt is parked until the user submits every required Blocking Input, after which that request claims the task and passes the submitted values to the runner in request memory. The task records the generated configuration and blocker metadata, not submitted values. The engine rejects empty or partial required-input submissions before changing state. It filters a submission to the authoritative blocker set before launching the runner; undeclared keys and non-scalar values never reach the run. A validation rejection may park the same attempt again only when the rejected value came from that submission and its key belonged to the authoritative Blocking Input set captured before the claim; invalid values inherited from an AI plan or default, and undeclared submitted fields, fail the attempt instead. Runtime, Gateway, generated-output, and artifact-structure failures cannot be repaired by that form, so they terminate the current attempt as `failed` and use ADR 0038 Redeploy for recovery. The reaper resolves legacy `blocked` rows with no Blocking Inputs, plus AI rows whose blockers lack the current artifact projection attestation, to `failed`, preserving a recognized reason from historical events when possible and otherwise using `unknown`; the terminal transition also makes those rows eligible for Devbox pause and retention.

## Considered Options

- Curated failure vocabulary only for every runner: rejected — the provider/Kubernetes error space is a long tail that will never be fully mapped, so direct/template runners retain their scrubbed ground-truth error. A curated vocabulary is deliberately used for the AI runner because no complete scrub set exists for arbitrary AI output.
- Show the raw error everywhere with no scrub: rejected — the terminal error is persisted in Postgres and can echo request credentials or unrelated provider data. Deployment configuration is intentionally inspectable; arbitrary operational error text is not a deployment-configuration artifact.
- Scrub at read time in the DTO only: rejected — it leaves a plaintext credential or provider secret in the database, independent of any single reader.
- A stronger scrub over arbitrary error text (regex secret detection): rejected — it cannot establish a complete redaction boundary and creates false confidence. The guarantee is limited to known sensitive values for deterministic runners; AI runner errors use the curated allowlist instead.
- A separate `system-blocked` status with an in-place Retry action: rejected — request-scoped kubeconfig cannot be recovered by a background runner, phase re-entry is not proven idempotent, and same-record retries would require attempt numbering and timeline reset semantics that ADR 0038 deliberately avoids through cloned Redeploy tasks.

## Consequences

The terminal failure write is the runner-specific safety chokepoint. Direct/template runners scrub and persist the provider error. AI runners persist the curated reason message and allowlisted structured details only. AI runtime-wait, readiness-observation, and input-rejection records use fixed messages and omit provider/command errors at write time; arbitrary Gateway event payloads are not persisted. The failure-summary logic resolves reason-code messages first; substring-matched classes (quota-exceeded, name-conflict, invalid-input, provider-unreachable) and raw-first-line fallback apply **only** to runners that surface raw errors, because those runners also expose the scrubbed detail needed to correct a false-positive class. The template runner's previously silent `template_declarations_unavailable` degrade remains a warning-severity event on the prepare step.

AI raw errors or transcript text must not be restored to persistence, UI, or Chat tool responses without first defining and testing a complete redaction contract for arbitrary Gateway, repository, and generated content. Existing runner-message schema and storage remain for compatibility but are not a public progress contract. The generated Sealos Template file, including its DSL expressions, input declarations, defaults, and options, is public task deployment configuration and is persisted unchanged. The runner performs no value or field-name sensitivity inference over that AI output. Submitted Blocking Input values and the Kubernetes YAML rendered from them are request-memory-only; rendered YAML is never copied into task artifacts, Timeline events, failure details, or Gateway transcripts. Legacy AI event text, provider statuses, unknown Timeline fields, and output signatures embedded in Timeline dedupe keys are replaced by the public read projection. A legacy prepared artifact is never upgraded to the current public projection version merely because a newer runner resumed it; only generated output retained as task configuration, or an already-versioned blocked resume, retains the version. New AI integration failures must attach a stable reason at their boundary and add its user message to the shared catalog. Existing rows remain compatible: missing or invalid AI reason data projects as `unknown`, while valid historical HTTP status and failure stage values survive the allowlist.
