# Surface Deployment Failure Reasons Behind a Per-Runner Scrub Gate

A failed Deployment Task must present an actionable Deployment Failure Reason in its failed Deployment Timeline Step rather than collapse to a generic "Deployment task failed." The reason has a stable machine-readable code and a curated user message. Deterministic direct/template runners may additionally expose their scrubbed provider/Kubernetes error as the Deployment Failure Detail. The AI runner instead exposes only allowlisted technical context — reason code, task phase, optional upstream HTTP status, and Task ID — because its raw Gateway and command errors can contain arbitrary repository or generated secrets. The existing `failureDetails` JSON and event payload carry the classification, so no database field or migration is required.

Because a displayed error can echo submitted input values, the ADR 0037 row-level secrets contract is extended to cover failure and error strings. For direct/template runners, every persisted copy of a terminal failure (event message, `payload.error`, `failureDetails`) is scrubbed of known sensitive values — raw, JSON-escaped, and base64 forms, via the same scrub used for rendered YAML — at the terminal failure write. Only the runner holds the plaintext sensitive values in memory, so it attaches its known sensitive-value set to the thrown error and the terminal write scrubs with it. Displaying the raw error and scrubbing it are the same decision — **a runner surfaces its raw error only if that runner's terminal error is scrubbed** ("scrub ⇔ raw display").

Template and direct runners pass the raw-display gate because their sensitive values are a structured, enumerable set (template args / settings values), so both enable the scrubbed raw error and raw-first-line fallback. The AI runner does not: its terminal write replaces the raw error with the curated message, persists only allowlisted structured failure details, and omits `payload.error`. Raw Gateway SSE payloads become empty invalidation signals instead of being forwarded to the browser; Gateway snapshots retain only lifecycle metadata, and transcript text is not copied into Deployment Task messages. Read-time DTO projection also removes raw AI errors from legacy `task.error`, `failureDetails`, event payloads, Gateway snapshots/messages, and generated `buildResult` as defense in depth. Unknown AI failures still expose the `unknown` code and Task ID with a support instruction.

The stable AI failure vocabulary covers GitHub authentication, repository clone, AI Proxy credentials, deploy/build runtime, skill installation, BuildKit startup and image-build failure, Gateway exposure/availability/5xx/timeout, missing deployment output, Apply/quota/readiness, interruption, maximum duration, never-started tasks, runner crashes, cancellation, and unknown failures. Integration boundaries attach the narrowest reason they can prove; Gateway failures retain only a validated HTTP status. Engine reaping uses the same vocabulary, and read-time timeline projection overlays a deterministic failed step for engine-resolved failures without incrementing the persisted timeline revision.

A failure reason does not introduce another waiting state. `blocked` retains its ADR 0037 meaning: the current attempt is parked until the user submits at least one explicit Blocking Input, after which that request claims the task and supplies the in-memory values needed to resume. The engine rejects an empty Blocking Input request before changing state. Runtime, Gateway, generated-output, and artifact-structure failures cannot be repaired by that form, so they terminate the current attempt as `failed` and use ADR 0038 Redeploy for recovery. The reaper resolves legacy `blocked` rows with no Blocking Inputs to `failed`, preserving a recognized reason from historical events when possible and otherwise using `unknown`; the terminal transition also makes those rows eligible for Devbox pause and retention.

## Considered Options

- Curated failure vocabulary only for every runner: rejected — the provider/Kubernetes error space is a long tail that will never be fully mapped, so direct/template runners retain their scrubbed ground-truth error. A curated vocabulary is deliberately used for the AI runner because no complete scrub set exists for arbitrary AI output.
- Show the raw error everywhere with no scrub: rejected — the terminal error is persisted in Postgres and can echo submitted secrets, violating the ADR 0037 no-secrets-at-rest posture (a gap that already exists latently for the unscrubbed error string today).
- Scrub at read time in the DTO only: rejected — write-time scrubbing is the guarantee under ADR 0037; a persisted plaintext secret is the exposure, independent of any single reader.
- A stronger scrub over arbitrary error text (regex secret detection): rejected — inconsistent with the rest of the system and a false-confidence rabbit hole. The guarantee matches the YAML scrub exactly — known declared/heuristic sensitive values — no weaker and no stronger.
- A separate `system-blocked` status with an in-place Retry action: rejected — request-scoped kubeconfig cannot be recovered by a background runner, phase re-entry is not proven idempotent, and same-record retries would require attempt numbering and timeline reset semantics that ADR 0038 deliberately avoids through cloned Redeploy tasks.

## Consequences

The terminal failure write is the runner-specific safety chokepoint. Direct/template runners scrub and persist the provider error. AI runners persist the curated reason message and allowlisted structured details only. AI runtime-wait and input-rejection events omit provider/command errors at write time, and arbitrary Gateway event payloads are not persisted. The failure-summary logic resolves reason-code messages first; substring-matched classes (quota-exceeded, name-conflict, invalid-input, provider-unreachable) and raw-first-line fallback apply **only** to runners that surface raw errors, because those runners also expose the scrubbed detail needed to correct a false-positive class. The template runner's previously silent `template_declarations_unavailable` degrade remains a warning-severity event on the prepare step.

AI raw errors must not be restored to persistence or UI without first defining and testing a complete redaction contract for arbitrary Gateway, repository, and generated content. New AI integration failures must attach a stable reason at their boundary and add its user message to the shared catalog. Existing rows remain compatible: missing or invalid AI reason data projects as `unknown`, while valid historical HTTP status and failure stage values survive the allowlist.
