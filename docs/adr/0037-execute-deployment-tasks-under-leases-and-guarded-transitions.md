# Execute Deployment Tasks Under Leases and Guarded Transitions

Deployment Task execution moves off request-scoped fire-and-forget promises onto a deployment-owned execution engine backed by the task's Postgres row. The task row is the only source of truth for task state. A guarded transition — a single-statement conditional update naming the allowed source statuses and the expected lease epoch — is the only way any code changes task status, and terminal statuses are immutable. Code that loses a guarded write re-reads the row and obeys it rather than retrying blindly.

Execution credentials pin execution to the credentialed request. Every Kubernetes operation a runner performs — manifest applies, template application, readiness observation — is authorized by the requesting user's kubeconfig, which exists only in request-process memory and is never persisted; the server holds no cluster credential of its own. (The Deploy Devbox API is the one exception: the server mints namespace-scoped JWTs from its signing key, so devbox pause/delete are server-executable without a user request.) A background worker that claimed a `queued` task from the database would hold a task it has no credentials to execute, so there is no worker pool. The Deployment Task Lease is claimed inline: task creation inserts the row as `queued` and immediately claims `queued → running` by compare-and-swap on the lease columns in the same request, launching the runner in that process with the kubeconfig held in memory; Blocking Input submission claims `blocked → running` the same way. `queued` is transient — a row still `queued` past a short start deadline (the process died between insert and claim) is resolved to `failed` with a never-started reason, never silently re-run.

A Deployment Task Lease is the only execution right. The launching process renews the lease on a fenced timer for as long as the run is in flight — lease expiry means the owning process died, not that runner code failed to reach a checkpoint between slow operations. A checkpoint is one operation that reads any pending Deployment Task Cancel Request. Runners touch task state only through a task handle (checkpoint, events, timeline, state, artifacts, request inputs, complete, fail, acknowledge cancel) whose every write is fenced by the lease epoch, so a superseded or stalled execution starves on 0-row updates and exits instead of corrupting state.

`blocked` is a parked, leaseless status: a runner that requests Blocking Inputs transitions, releases its lease, and exits. Submitted Blocking Input values, regardless of field name or UI type, are request-memory-only: the resumed submission passes them directly to the runner but does not store them on the task. The task retains the declared input schema and AI-generated deployment configuration needed to reconstruct the form, not the submitted values themselves. The input submission request performs the `blocked → running` claim and resumes the runner from that stored configuration plus the fresh submitted values. An AI Runner resumed this way re-attaches to its Deploy Devbox and Codex Gateway session through the identifiers already persisted on the task.

Deployment configuration is a task-owned persisted artifact. AI-generated inline Sealos Template source, delivery manifest, defaults, options, and generated args are public deployment configuration and are retained unchanged. The source is opaque Sealos DSL, not standard YAML: it is never scanned for values, parsed as a whole, serialized, redacted, or normalized before its `${{ if/endif }}` expressions are rendered. Only the leading Template header is structurally validated as YAML to derive the input form; resource documents are rendered from the preserved DSL and only then parsed as Kubernetes YAML. Before a Blocking Input form is shown, the header declarations are resolved into a separate public render state; it pins generated defaults and the planned instance name across a blocked resume without modifying the source. `secret` and `password` may select a masked form control, but neither a declaration nor a field name establishes that generated content is secret. In particular, no shape of `options`, default, key, or value in AI output is a sensitivity signal. Inputs identify values that must be collected from the user. Those submitted values are never persisted, and the rendered Kubernetes YAML that contains them is kept in memory only for Apply. Textual redaction or placeholder replacement must never mutate the stored source, because a YAML scalar, sequence, map, string literal, and Sealos expression are materially different deployment inputs. This policy applies only to deployment configuration: request credentials such as kubeconfig, GitHub OAuth tokens, Devbox JWTs, and AI Proxy credentials remain request-scoped and are never persisted. Timeline events, failure details, and Gateway transcripts remain operational records rather than copies of the deployment configuration.

A reaper sweep resolves stalls; every deadline comparison happens in SQL against the database clock, so process clock skew cannot misjudge liveness. An expired lease on an active task resolves to `failed` with an interrupted reason — or to `cancelled` when a Cancel Request is pending, because terminal status reports the outcome of the user's intent while internals belong in failure details and events. A Cancel Request unacknowledged past its deadline is resolved to `cancelled` regardless of lease liveness; the terminal guard then starves any still-live runner. A claim held longer than the maximum active-run duration resolves to `failed` with a timeout reason, because a lease renewed by a live process no longer proves the run is making progress. The same sweep pauses the per-task Deploy Devbox of any terminal task whose runner did not pause it (crash, forced resolution) using the server-minted devbox JWT, so an interrupted task's devbox never idles until retention. Every engine-resolved transition records a task event naming the verdict and its reason, so a timeline always explains a system-decided outcome. Interrupted tasks are not resumed: recovery is an explicit Redeploy.

On shutdown the process stops launching runs, aborts in-flight runners, and resolves its own leases to `failed` with an interrupted-by-shutdown reason via guarded writes — honest state immediately, rather than a stuck spinner until another process's reaper notices the expired lease.

Reaching `completed` still requires Deployment Result Readiness (ADR 0028), and the runner owns the readiness wait under its lease with abort support. A readiness deadline fails the task with a readiness-timeout reason instead of completing it, preserving created resources; the prior behavior of completing on timeout violated that ADR. The prior read-path completion — snapshot and timeline reads observing readiness and writing `completed` — is removed outright: reads never write status. Task creation resolves the Deployment Target synchronously (idempotent — resolved Project identity is cached on the task per ADR 0023 and never re-created), inserts the task as `queued`, claims inline, and reports the stored status truthfully.

One global Postgres NOTIFY channel replaces the in-process listener maps, so projection and timeline streams (ADR 0025) no longer assume a single server process. The payload carries only identifiers (namespace, project, task); subscribers re-read the row, and stream handlers subscribe before their bootstrap read so no update falls between snapshot and subscription. The listener holds a dedicated connection and re-bootstraps subscribers after a reconnect, because notifications during the gap are lost. Retention-purge removals are the one case where re-reading is impossible, so the purge notification's identifiers are themselves the removal event.

## Considered Options

- Keep launching runners as fire-and-forget promises from route handlers: rejected because a server restart leaves `running` rows orphaned forever, cancellation has no enforcement point, and a re-run can start a second concurrent runner against the same task.
- A background worker pool claiming `queued` tasks (this ADR's original draft): rejected because runner credentials are request-scoped — the user's kubeconfig authorizes every Kubernetes operation and is never at rest, so a claiming worker could not execute what it claimed. Inline claims keep every safety property (single execution right, fenced writes, honest interruption) without a credential store.
- Persisting the user kubeconfig (encrypted column or cluster Secret) so any process can execute any task: rejected — cluster credentials are the broadest secret the platform touches, and no queue capability is worth putting them at rest.
- Execute deployment tasks in the Go API service: rejected because the AI Runner is bound to the TypeScript runtime (Deploy Devbox SDK, Codex Gateway sessions, UIMessage transcripts) and a port buys no user-visible capability.
- Adopt an external queue or workflow engine (Temporal, BullMQ with Redis): rejected because it adds an operated dependency for a workload of single-digit tasks per minute, and the credential model would idle any cross-process queue anyway.
- Persist generated Sealos Template source and generated configuration as task deployment configuration: accepted. The source is an inspectable Sealos DSL submission and is kept byte-for-byte so persistence cannot corrupt its conditional syntax before rendering. No content or field-name sensitivity inference is performed over AI output. Submitted Blocking Input values remain request-scoped regardless of type or name, and rendered Kubernetes YAML is Apply-only memory. This does not authorize persistence of request credentials.
- Renew the lease only at runner checkpoints so a hung runner self-heals through lease expiry: rejected because any single operation slower than the lease — a slow Deploy Devbox start, a long Codex Gateway turn — would be misdeclared an interrupted failure while its side effects continue; the maximum active-run duration covers true hangs instead.
- Model cancelling as a status instead of a Cancel Request column: rejected because the intent overlays every active status; a status would multiply the transition table and erase which phase-specific stop behavior applies.
- Resume interrupted tasks after a crash: rejected for now because per-phase re-entry is unproven — an AI Runner cannot be safely re-entered mid-turn — and an honest interrupted failure plus Redeploy is preferred. A resume whitelist for pre-apply deterministic runs may be revisited.
- Allocate task event sequence numbers with an advisory lock and `max(seq)+1` (status quo): replaced by a global sequence default so event inserts are single-statement and lock-free; per-task ordering only needs monotonicity, not density.

## Consequences

`deploy_tasks` gains `cancel_requested_at`, `lease_owner`, `lease_expires_at`, `lease_epoch`, and `lease_claimed_at` (the anchor for the maximum active-run duration, reset on every claim so parked `blocked` time never counts); `heartbeat_at` is dropped because lease expiry is the liveness fact. `deploy_task_events.seq` defaults from a global sequence. Partial indexes cover the reaper's scans (leased statuses by expiry, `queued` by age, terminal by completion time). Rows still in active statuses when the engine ships are marked interrupted failures once at rollout.

The engine module becomes the only status writer, and constrains itself to single-statement conditional updates — no advisory locks, no multi-statement transactions — using a CTE where a transition and its event must land together. Runners receive the task handle and never import task storage; integrations (Kubernetes apply, Deploy Devbox, Codex Gateway) are stateless clients that accept abort signals. Lease renewal, checkpoint, reaper, cancel-acknowledgement, maximum active-run, and queued start-deadline cadences are tuning constants (initially 60s lease renewed on a 20s timer, ≤20s checkpoint, 30s sweep, 90s cancel deadline, 30min maximum active run, 120s start deadline), not contract. The engine runtime is an HMR-safe per-process singleton started with the server boot hook alongside migrations.

Task list reads gain cursor pagination (on creation time and id, which do not move under updates) and status filtering so any future task surface reads the same API. Creation responses stop fabricating statuses ahead of the stored row. CONTEXT.md gains Deployment Task Lease and Deployment Task Cancel Request.
