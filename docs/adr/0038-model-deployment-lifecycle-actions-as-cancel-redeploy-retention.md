# Model Deployment Task Lifecycle Actions as Cancel, Redeploy, and Retention

A Deployment Task exposes exactly two in-place actions — a Deployment Task Cancel Request and Blocking Input submission. Recovery is Redeploy, which is task creation; cleanup is Deployment Task Retention, which is automatic. `failed` and `cancelled` are pure terminal statuses with no outgoing transitions, and there is no user-facing task deletion.

Cancelling stops the deploy workflow and never deletes or reverts applied resources. `queued` and `blocked` tasks cancel immediately; `running` and `applying` tasks acknowledge cooperatively at a checkpoint, with abort signals propagated into gateway turns, devbox operations, and readiness waits. The direct runner stops between resource applications; template application is one atomic provider call, so a template task cancels either before or after application with no partial state. Cancel stays available during `verify` — a phase within the `applying` status (ADR 0023), not a status of its own — where it means "stop waiting" and is symmetric with a readiness-timeout failure. There is one `cancelled` terminal status; the artifact summary and Deployment Task Timeline distinguish nothing, partially, or fully applied, and every applied resource is itemized as the basis for manual compensation. After a deadline-forced cancel that itemization is best-effort — a still-live runner's final apply can land after its recording writes are already fenced off — so the canvas, not the task record, stays the source of truth for what exists. Applied resources remain first-class canvas resources whose deletion is always an explicit canvas action.

A per-task Deploy Devbox is paused at every terminal outcome, not deleted: the runner pauses it on its own completion, failure, and abort paths, and the reaper pauses it for engine-resolved terminals (interruption, forced cancel, timeout) using the server-minted devbox JWT — the one execution credential the server holds — so no devbox idles until retention because its owning process died.

Redeploy is the only recovery path from `failed` or `cancelled`: a new Deployment Task cloned from the predecessor's Deployment Source and Deployment Target, with lineage recorded on the new task. A verbatim clone and an edited redeploy (deploy pane prefilled from the predecessor's source) are the same mechanism. A clone reuses result identities the predecessor already allocated — in particular the random-suffixed template instance name — so redeploying over preserved resources converges on the same resources instead of creating a second template instance. Identities copy only when the clone's effective target matches the predecessor's resolved Project: an edited redeploy that retargets gets fresh identities, because a namespace-scoped instance name must never travel to a Project where its resources never existed. Allocated identities are recorded first-class on the task at allocation time — persisted before any external apply or provider call uses them, so an identity can never be allocated and then lost to a crash — and copied onto the clone's row at creation, so a redeploy chain keeps them even when an intermediate task never reached artifact generation or the original predecessor has been purged. At most one active clone per predecessor is enforced structurally by a partial unique index on the lineage column over active statuses: a simultaneous redeploy loses the insert itself and receives the conflict with the winner's snapshot, so two recovery attempts can never race the same preserved resources. Creating a Redeploy dismisses the predecessor's Deployment Task Dock reminder, and redeploying onto existing resources warns once that manual edits since the failed run will be overwritten. Blocking Input values are re-asked on every redeploy because they are never stored; non-sensitive fields prefill from the deployment plan's declared defaults — never from a prior submission — and sensitive fields are always re-entered.

Deployment Task Retention replaces deletion. Terminal tasks — with their events, runner transcripts, and per-task Deploy Devboxes — are purged after a fixed window, initially 30 days. A purge deletes external leavings first (the per-task devbox, via the server-minted JWT) and then the rows, and retries on the next sweep if any step fails, so a half-purged task is re-swept rather than stranded. Active and `blocked` tasks are never purged; a task waiting on inputs keeps its dock attention indefinitely because waiting on the user is correct behavior, while `cancelled` is not attention-needed at all and shows only a brief dismissible notice. `failed` remains attention-needed until dismissed or superseded by a Redeploy.

Action conflicts resolve by guarded transition, never by arbitration code, under one idempotency rule: an action whose intent the current state already satisfies returns success with the current snapshot (repeated cancel), an action whose intent can no longer be satisfied returns a conflict carrying the snapshot (cancel after completion, simultaneous redeploy losing the guarded insert), and surfaces reconcile from the snapshot instead of showing an error for an outcome the user effectively got. A clone request follows the same rule: a predecessor that is not `failed` or `cancelled` returns a conflict carrying its snapshot, and a purged or unknown predecessor is a plain not-found — never a silent fresh create, which would re-allocate identities the preserved resources still hold.

This release adds no new product surfaces. The Deployment Task Timeline pane gains cancel and redeploy actions; dock chips stay a notification and re-entry affordance (status, click-to-open, and a terminal-only dismiss) and carry no inline lifecycle actions (see Amendment below). The Deployment Placeholder Node menu (opening the timeline and cancel only, because terminal tasks have no canvas presence per ADR 0024) is deferred — the canvas has no context-menu infrastructure yet, and clicking a placeholder already opens the timeline pane where cancel lives. A platform notification center — which may absorb the dock and host deployment history — is deferred to its own ADR; this decision only keeps its doors open through the shared notify channel, the paginated task list API, and recorded lineage. Dismissal state stays client-local in v1 — a Redeploy dismisses its predecessor's reminder because surfaces derive supersession from the clone's lineage — and a persisted per-task-and-user read-state is deferred to the notification center.

## Considered Options

- Retry as a new attempt on the same task record (the GitHub Actions model): rejected because comparable deployment platforms uniformly model recovery as a new record, a same-record retry needs attempt numbering, timeline resets, retry races, and stale-intent clearing that the clone model deletes wholesale, and it forks verbatim retry and edit-then-redeploy into two mechanisms where the clone model has one.
- A user-facing delete endpoint and affordance: rejected because no v1 surface has history as its job — dock dismissal already hides acknowledged failures — and per-record deletion is the exception among comparable products while automatic retention is the norm. Reconsidered when the notification center exists.
- Rolling back applied resources on cancel: rejected because partial success is often the desired outcome, rollback has its own failure modes and half-failed states, and resource deletion is an explicit canvas action — consistent with preserving template resources on readiness timeout.
- Refusing cancel once apply has finished ("too late to cancel"): rejected because verify is the longest-running phase and stopping the wait is the most common reason to cancel; the resource outcome is reported honestly instead of gating the button.
- A compound cancel-then-delete gesture: rejected as client-side choreography that can strand halfway; dismissal covers attention cleanup and retention covers records.
- A project deployment history side pane in v1: deferred because the notification center decision would supersede its placement, and its main unique job would have been hosting the delete affordance this ADR removes.
- Diff detection before redeploying over manually edited resources: rejected for now in favor of the one-line overwrite warning.
- Guarding concurrent redeploys client-side only (disabled buttons): rejected because identity reuse makes a duplicate clone strictly more dangerous than before — two active clones would converge on the same preserved resources concurrently; the partial unique index closes the race in one statement.

## Consequences

`deploy_tasks` gains `retried_from_task_id` with no foreign key, because predecessors are purgeable, plus a partial unique index over active statuses enforcing one active clone per predecessor. The HTTP surface shrinks to create (also serving clones), list, snapshot, cancel, input, and the existing streams: `DELETE /:id` (which actually cancelled) and `POST /:id/retry` are removed, and cancel moves to `POST /:id/cancel`. Chat deployment tools mirror create, cancel, and explain.

Creation copies the predecessor's recorded result identities onto the clone before any artifact generation, and generation reuses a recorded identity instead of allocating a fresh one. This also fixes an existing defect: a retried template deployment allocated a fresh random-suffixed instance name while the previous instance was preserved, deploying a second instance.

Accepted gaps until the notification center ADR: dismissed failures have no re-entry surface, and cancelled tasks lose their redeploy entry once their notice is gone (the deploy pane covers recovery). CONTEXT.md gains Redeploy and Deployment Task Retention.

## Amendment (2026-07-08): Dock chips are notification-only, dismiss is terminal-only

The original decision put cancel and redeploy actions on dock chips as well as the timeline pane. In use this made the chip cluttered and ambiguous — icon-only `Ban`/`RotateCcw` controls easy to misclick on a small chip, duplicating the labeled, confirm-gated buttons already in the Deployment Task Timeline pane. This amendment narrows the chip to a pure notification and re-entry affordance:

- **No inline lifecycle actions on the chip.** Cancel and Redeploy live only in the Deployment Task Timeline pane, which the chip opens on click. Nothing is stranded: clicking a failed chip reaches the pane's Redeploy in one extra step, and the ADR already accepts that a dismissed failure has no re-entry surface.
- **Dismiss (✕) is a terminal-only action.** It appears only for terminal statuses (`failed`, `completed`, `cancelled`). In-progress statuses (`queued`, `running`, `applying`, and `blocked`, which keeps its dock attention indefinitely) show no ✕. This removes a real defect: because dismissal is keyed to the projection version (`updatedAt`), pressing ✕ on a running task recorded a version that the next projection update immediately superseded, so the chip reappeared — a control that looked actionable but was a no-op mid-deploy.
- **No confirmation dialog on dismiss.** With dismiss restricted to terminal states, the accidental-loss risk is limited to a failed chip whose task is still retained and recoverable via the deploy pane; a blocking modal is heavier than the cost warrants. A non-blocking Undo affordance was considered and also declined for v1.

To stop an in-progress deployment the user cancels it in the pane; it then becomes `cancelled` and rides the brief dismissible completion notice. This keeps the invariant that a still-running deployment cannot be hidden from the dock.

## Amendment (2026-07-10): Failure cleanup only for provably this-run partial applies

The original runner deleted a failed template deployment's labeled resources on every non-abort failure. That polarity contradicted this ADR twice over: a readiness timeout after a successful apply swept live workloads and PVCs that ADR 0037 promises to preserve, and on a Redeploy — which reuses the recorded instance name to converge on preserved resources — the label-selector sweep deleted the predecessor's resources on any failure, including ones before this run applied anything. This amendment narrows failure cleanup to the one case where deletion is provably scoped to this run:

- **Cleanup requires both a typed apply-stage failure and a freshly allocated identity.** The apply provider call marks its own errors (`stage: "apply"` on the attached failure details); cleanup runs only when that marker is present and the template instance name was allocated by this run. Only then does the selector provably match nothing but this run's partial creation.
- **Everything else preserves resources.** Readiness timeouts (failing with the readiness-timeout reason per ADR 0037), post-apply persistence errors, pre-apply generation errors, and any failure on a reused identity leave resources untouched — their deletion stays an explicit canvas action, and a Redeploy converges on whatever remains.
- **Misjudgment degrades toward preservation.** A lost or absent stage marker skips cleanup; the failure summary for a readiness timeout tells the user the created resources were preserved and that Redeploy reuses them.
