# Snapshot Glass: Replace the Live Backdrop-Filter Sheet with a Pre-Blurred Texture

The canvas glass sheet (ADR-visible as `canvas-glass-{sheet,geometry,store}` in `packages/ui`) used a live `backdrop-filter: blur(40px)`. Chromium keeps no cache for backdrop-filter output — it re-reads the framebuffer and re-blurs inside every produced frame whose damage overlaps the sheet, even when the change is painted *above* the glass (status-dot pings), and no platform switch decouples this (backdrop root, `isolation`, `contain`, `will-change` all ruled out; shrinking the radius is useless because Skia downsamples σ>4). Measured on the 12-node prototype harness: live glass 939.7 ms/s cross-process task time vs 315.1 ms/s for a pre-blurred texture — exactly the 314.8 ms/s glass-off floor. We now pre-blur the backdrop into **two textures mounted as children of the masked sheet** (`canvas-glass-snapshot.ts`), split by how they move: the **ambient plane** (surface color + bloom) is screen-space — the bloom never moves while the user pans — so its canvas is counter-transformed against the viewport every frame (a compositor-cheap inline transform), keeping the glow flowing through the windows continuously exactly like live sampling; the **content plane** (dot grid + edges) is flow-space and transparent, riding the viewport transform natively above it. Panning regenerates *nothing*; regens happen only when inputs change (node geometry/edges throttled during drags, zoom settle, theme, container size). A first single-texture cut baked the bloom into the flow-space texture and re-captured on pan settle — panning froze the glow relative to the windows and then visibly snapped at settle; the two-plane split is what makes panning continuous. Once both textures are painted the sheet gets `data-snapshot="ready"` and CSS turns the live blur off; until then — and on any unsupported browser or failed color resolution — the live backdrop-filter keeps rendering unchanged (correctness over cost, never a broken frame).

## Considered Options

- Keep the live backdrop-filter (status quo): rejected — the per-frame tax is structural to Chromium's readback model (`.obsidian/research/2026-07-10-glass-sheet-per-frame-tax.md`, source-cited) and multiplies against every animation on the canvas, negating the shipped heartbeat/idle work.
- Capture via a computed-style-inlined `foreignObject` clone of `.canvas-surface` (the prototype's approach): rejected for production — regeneration cost scales with live DOM size (per-element style inlining), rasterization is async (decode roundtrip on every regen), it can only capture what is on screen (a pan reveals unpainted texture until the next settle), and it is monolithic where the blurred-twin future needs per-layer separability. Its one real advantage — engine-exact painting — turned out to be reproducible programmatically (see Consequences: equivalence engineering).
- Programmatic layer redraw sourced from the live DOM (chosen): bg fill + bloom gradient + dot grid + edge `d`-paths redrawn from computed styles into a canvas. Synchronous, cost-bounded, covers off-screen sheet regions, untainted, and naturally a composable layer list.
- Re-rendering the whole canvas in WebGL/WebGPU with shader blur (the Figma shape): out of scope — a rendering-engine rewrite; recorded as the endgame if the product ever needs rich animated backdrops beyond the blurred-twin constraint below.

## Consequences

### Architecture

- `canvas-glass-snapshot.ts` owns capture: pure geometry/color helpers (unit-tested, including `glassAmbientPlacement` — the per-frame screen-pinning inverse transform), DOM readers (`readGlassBackdropTheme`, `collectGlassEdgeStrokes`), the flow-space `GlassBackdropLayer[]` content plane (dots → edges) plus the ambient scene painter, `renderGlassContent` / `renderGlassAmbient` (draw scene → blur once into the mounted canvas), and `createGlassSnapshotController` (triggers, scheduling, both placements).
- `CanvasGlassSheet` feeds the controller one cheap frame observation per rAF-coalesced store sync (`{edges, geometry, transform, width, height}`); the existing mask sync is unchanged. In the same sync, the content canvas stays pinned to its captured flow rect (`captured rect − sheet rect`) and the ambient canvas is re-pinned to screen coordinates (inline `transform`, origin 0 0 — during pan this is the only work, a compositor-cheap style write on frames that are already doing full React Flow work).
- Regeneration triggers: node-geometry signature change and edge-array change (trailing throttle 160ms — this is what refreshes edges during node drag), zoom settle and container resize (160ms debounce after the last change; zoom changes the content resolution, the dot phase, and the ambient's baked σ — the live blur is declared in flow px, so its screen-space σ is `radius·zoom`), theme mutations on `<html>` (class/style/data-theme observer), and first activation (immediate). **Pan triggers nothing.** The ambient render is memoized by (theme colors, container, zoom, blur radius, raster scale), so drag-throttled content regens skip it. Regens defer while `document.hidden` and flush on visibility.
- The ambient raster pads the container by 3σ (screen px) so blur never bleeds transparency into container-edge windows; during a zoom gesture its baked σ lags until settle, which is invisible on a smooth field.
- Hybrid unchanged: overlapping nodes keep their own live backdrop-filter (they sample sibling nodes, which a backdrop texture cannot reproduce). Verified: overlap-pair windows diff 0.000/255 between modes.
- Support gate (`detectGlassSnapshotSupport`): a verified float16 2d context plus `ctx.filter`. Safari currently fails the gate and keeps live glass (acceptable degradation; re-evaluate when Safari ships float16 canvases). Test escape hatch: `<html data-canvas-glass="live">` forces live mode; `data-regens` on the texture counts regenerations for tests.
- The texture resolution follows zoom × devicePixelRatio, capped at 4096 px on the long side (`pickCaptureScale`) — blurred content survives downscale invisibly, so huge sheets cannot allocate unbounded backing stores.

### Equivalence engineering (the tripwires)

The equivalence bar is per-window channel-mean delta ≤ 0.5/255 against live glass, including a bloom-heavy window — pixelmatch alone is anti-aliasing-tolerant and passed a +10/255 veil at "0.031% diff" during the prototype. The bar's derivation: the failure modes it guards against sit far above it (color-management veils ≥1–2/255, stale/misaligned textures ≥5/255), while the two-plane split carries an irreducible second-order blur-decomposition term — `blur(content over ambient)` vs `blur(content) over blur(ambient)` differ where the ambient gradient varies within the kernel — measured ≤0.4/255 steady-state and ≤0.55 in the worst post-interaction pose. Getting to sub-veil accuracy at all required four discoveries, each a regression tripwire — changing any of these will look correct in review and only show up in channel means:

- **float16 canvases** (`GLASS_CONTEXT_SETTINGS`): an unorm8 texture quantizes the smooth backdrop once per draw, and over a slowly-varying field the rounding error is locally constant — a measured ≈0.5–0.8/255 flat veil. float16 leaves final-composite quantization as the only rounding, same as live.
- **Blend in gamma sRGB, not display-p3**: Blink rasterizes the page's tiles in gamma sRGB — the `::before`-over-background alpha blend and stroke antialiasing happen there. A display-p3 canvas blends in gamma P3 and measured a flat ≈1/255 red bias. The scene canvas is therefore `colorSpace: "srgb"` + float16 — *extended* sRGB, so wide-gamut values survive as out-of-[0,1] floats instead of clamping (the original P3 "+10 RGB veil" failure mode of 8-bit sRGB intermediates).
- **Pre-flatten the bloom over the background** (`bloomGradientStops`): the CSS gradient's OKLab ramp is sampled densely (canvas interpolates between stops in the canvas color space, not OKLab; error ∝ 1/N² per segment), each sample converted to sRGB and alpha-blended over the surface color numerically, then emitted as opaque stops — the ambient texture never alpha-composites the bloom itself, and the background fill uses the same numeric source so the gradient's edge is seamless.
- **Match Blink's tiny-dot rasterization** (`drawDotsLayer`): Blink fills the xyflow pattern's r=1-device-px dot at full pixel coverage (a square); canvas `arc()` true-AA gives ~0.6 coverage — a uniform ≈0.3/255 energy deficit after the blur. Dots draw as squares while radius × scale ≤ 2 device px. The dot grid's flow phase includes xyflow's `|| 1 +` operator-precedence quirk (`dotGridPhase`), asserted against the pattern math in unit tests.
- Also load-bearing: the blur radius is read from `--canvas-glass-blur-radius` on the sheet (a themed override must move both pipelines), and edge strokes are redrawn from the live `d` attributes and computed styles, so whatever xyflow painted is what the texture reproduces.

### Guard and evidence

- `apps/registry/src/app/glass-equivalence` is a committed deterministic fixture (5 nodes incl. a bloom-center window and an overlapping pair, 3 dashed edges, fixed viewport; `?mode=live|off`, `?pings=1`, `?blur=N` diagnostics). `apps/registry/e2e/glass-equivalence.mjs` (`bun run e2e:glass`, playwright-core over installed Chrome, no browser download) screenshots snapshot vs live and asserts per-window channel means ≤0.5/255 **and** pixelmatch ≤1%. Current steady-state: worst window 0.004/0.314/0.388, pixelmatch 0.000% everywhere. There is no repo CI test pipeline today (docker/helm only); the spec is the runnable guard to wire in when one exists.
- Interaction equivalence (pan, ctrl-zoom, node drag driven via CDP identically in both modes): **mid-pan (buttons held) and post-pan deltas are identical** (worst 0.541/255 at both sample points — continuous, nothing snaps at settle) with **zero regens during pan**; zoom +1 and drag +2 regens fire and land ≤0.52. Staleness or misalignment would read as 5–50/255; the residual is the pose-dependent decomposition term plus sub-pixel dot-raster phase, not staleness.
- Idle cost: with snapshot ready the sheet's computed `backdrop-filter` is `none` — the tax source is removed outright, and the controller does no per-frame work when the store is idle (regens are purely event-driven). `GLASS_E2E_TRACE=1` runs headed median-of-3 traces (headless never produces per-vsync frames, so the tax does not manifest there); on a loaded dev box the live-vs-off delta sits inside ±60 ms/s machine noise at this fixture's scale, so the prototype's quiet-bench measurement (939.7 → 315.1 ≡ floor 314.8 ms/s) remains the authoritative cost evidence.
- Registry node previews (which mount the same canvas) verified: sheet ready, live blur off, one texture, zero console errors.
- The theme trigger is implemented but currently unexercised — the app pins `forcedTheme="dark"` (`next-themes`); when a second theme ships, theme switches regenerate via the `<html>` attribute observer.

### Future animated backgrounds: the blurred-twin constraint

The two-plane split is the seam for a future ambient canvas background animation — **the ambient plane is already the first blurred twin**, "animated" by the per-frame viewport counter-transform. A new animated layer joins the same way: pre-blur the layer once, then run the *same* animation timeline on the blurred copy inside the glass while the sharp original animates below the sheet. This works because Gaussian blur commutes with translation exactly and with small scale/opacity changes approximately. It therefore imposes a hard design constraint, recorded here as the canonical reference: **any future canvas-background animation must be transform/opacity-only.** Content mutation (hue rotation, gradient shifts, morphing, particles, video) invalidates the pre-blurred copy every frame and reintroduces the per-frame tax — the whole economy of this ADR. Low-frequency content changes (regenerate-on-change) and short-lived exceptions that temporarily fall back to live blur are fine; continuous per-frame content mutation in a standing background is not.
