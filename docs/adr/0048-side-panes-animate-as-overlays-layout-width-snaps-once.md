# Side Panes Animate as Overlays; Layout Width Snaps Once

Opening or closing a workspace side pane used to animate the pane's layout `width` (the assistant pane put `width` in its transition-property list; the project index animated its `.sidePaneReserve` spacer), so every frame of the 340ms motion re-laid-out the whole workspace. On the canvas route each of those frames cascaded: layout → canvas container resize → xyflow `ResizeObserver` → glass-sheet mask geometry resync. On the index route each frame additionally re-evaluated container queries (`cqw` padding, `@container` breakpoints) and re-laid-out the project list. Layout properties cannot animate off the main thread, so no tuning of the animation makes this cheap. We now animate panes purely as transform+opacity overlays and change layout width in exactly one snap per toggle, choreographed so the reflow happens where it cannot be seen: on open the reserve snaps only after the enter transition settles (the reflow lands underneath the opaque pane); on close the reserve releases at t=0 (the expansion happens under the still-covering pane, which then fades out over the already-settled layout). On the index route, where the snapped content is the visible page body, a FLIP pass translates the centered explorer column from its old position to its new one in sync with the pane's motion, so the perceived glide is unchanged while costing only a compositor transform.

## Considered Options

- Keep animating `width` (status quo): rejected — width is a layout property; the per-frame relayout, canvas `ResizeObserver` storm, and container-query re-evaluation are structural to that choice (render-perf audit 2026-07-10, F22), not fixable by easing or duration.
- Fold the assistant pane into the canvas viewport-insets system (canvas stays full-bleed forever; the pane's width feeds `useProjectCanvasViewportInsets` like the node side pane already does): deferred — it would also eliminate reflow during drag-resize, but it moves the pane out of the flex flow entirely, entangles minimap/controls coverage with inset bookkeeping, and does nothing for the index route (a content grid genuinely needs its width). Recorded as the follow-up direction if drag-resize reflow shows up in profiles; open/close was the frequent, janky path.
- Snap the index reserve without FLIP compensation: rejected — the centered project list is the page's primary content, and a visible half-pane-width jump reads as breakage. The FLIP glide restores the exact perceived motion for the cost of one transient transform. (Width itself still snaps: only position can be compensated with transforms; compensating width would mean `scale`, which distorts glyphs.)
- Animate a `transform: scaleX` on the squeezed content instead of width: rejected — non-uniform scale distorts text and canvas content.

## Consequences

- The assistant pane is an absolute, right-anchored overlay (`z-30`) with a constant rendered width, animated with the same two-layer recipe as `side-pane.tsx`: the outer clip box fades and nudges 24px (`project-surface-slide-x-offset`) while the inner chrome surface slides its full width (`project-surface-slide-x-full`, `transition-transform`), so the panel physically drives in from the right edge. (A first cut animated only the outer fade+nudge; with the width growth gone that read as a blink-in and was upgraded to the full slide.) A zero-transition in-flow spacer (`data-slot="assistant-pane-reserve"`) carries the layout width: `0` while closed or animating open, the pane width once settled.
- Enter settlement is detected by `transitionend` on the pane, with a timeout fallback (`ASSISTANT_PANE_ENTER_SETTLE_MS`, which mirrors `--project-surface-motion-enter-duration` plus slack) and an immediate path for `prefers-reduced-motion`. Mounting with the pane already open reserves immediately — there is no enter transition to wait for.
- Measured after-evidence (Chrome trace, real project): 2–3 Layout events for an entire open/close cycle window versus per-frame relayout for 340ms before; the reserve takes exactly two values (0 and the pane width) over every sampled frame.
- Right-anchored canvas widgets (minimap, zoom controls) no longer glide with the squeeze: on open they pop out at the pane's left edge once the reserve snaps; on close they teleport under the covering pane and are revealed by its fade. This is the accepted visual trade.
- Drag-resize (`paneResizing`) and window resizes (`viewportResizing`) keep the previous live width tracking with transitions disabled; only open/close semantics changed. The pane resizer renders only once the pane is settled, so it cannot sit at a stale position mid-animation.
- The index `.sidePaneReserve` never transitions, and the explorer container's `transition-[padding]` was removed — the container-query padding snaps in the same layout pass the FLIP compensates. The FLIP baseline is measured with `offsetLeft` (transform-immune) and refreshed by a `ResizeObserver`, so window resizes between toggles cannot skew the glide.
- Regression tripwire: re-adding `width`/`max-width` to any transition-property on these surfaces, or giving the reserve a transition, silently reintroduces the per-frame reflow — it will look correct in review and only show up in traces. This ADR is the record of why those properties must stay snap-only.
- The chat pane content now keeps its real width while hidden (previously it was laid out at width 0 when closed), so toggling no longer re-wraps the transcript.
