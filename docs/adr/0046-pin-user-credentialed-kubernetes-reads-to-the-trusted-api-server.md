# Pin User-Credentialed Kubernetes Reads to the Trusted API Server

The Go API authenticates a caller by its own kubeconfig (`Authorization: Bearer <url-encoded kubeconfig>`) and authorizes every namespace-scoped operation by making the apiserver call **as the caller** and letting Kubernetes RBAC decide. That model is only sound if the apiserver answering is the real cluster. The `rest.Config` built from a caller's kubeconfig is therefore constructed with its **server, CA bundle, and TLS-verification pinned to the platform-trusted apiserver** — an explicit `K8S_API_URL`, or the in-cluster `KUBERNETES_SERVICE_HOST`/`KUBERNETES_SERVICE_PORT` plus the mounted service-account CA — while only the caller's identity (bearer token or client certificate) is taken from the kubeconfig. The client-supplied `server`, `certificate-authority`, and `insecure-skip-tls-verify` are ignored. This is enforced at the single point where every such config is built — `middleware.ResolveContext` and `middleware.RestConfigFromAuth` now share one constructor (`restConfigFromClientcmdConfig`) that pins before returning — so no route or service can opt out and no future endpoint can reintroduce the gap.

This closes the residual that ADR 0045 recorded and left out of scope: a caller could point its kubeconfig at an apiserver it controls that returns fabricated `200`s, satisfy the "GET the target with your credentials" authorization gate for any namespace, and then have the *real* query run against a shared backend under the service's own access — VictoriaMetrics (`VMSELECT_URL`) for workload telemetry, shared Postgres (`DATABASE_URL`) for AP version history. It is the Go-API analog of security-audit finding F5 (the UI's fail-open kubeconfig verification, since fixed by pinning namespace access reviews to the same trusted server) and resolves the audit's cross-cutting "fail-open on server trust" theme for the Go side. Pinning at the source, rather than per endpoint, is deliberate: the only consumer of the kubeconfig's declared server was `ResolvedContext.Server`, which nothing routes on, and the platform is single-cluster with no hub-and-spoke routing — so for a legitimate caller, whose kubeconfig already names the real cluster, pinning is a no-op, and for a hostile one it redirects the read back to the real apiserver, where RBAC denies the cross-tenant access the forged server was meant to fake.

The path is fail-closed. When neither an explicit `K8S_API_URL` nor in-cluster coordinates are present, the constructor returns `ErrNoTrustedAPIServer` and the request fails rather than trusting a client-named server. In-cluster deployments need no new configuration — `KUBERNETES_SERVICE_HOST`/`PORT` and the service-account CA are already injected into every pod. Off-cluster and dev deployments must set `K8S_API_URL` (https only), and `K8S_API_CA` when the apiserver's serving certificate is not chained to the process's default trust store; this mirrors how the UI's F5 fix is scoped.

## Considered Options

- **Pin only the two resolvers that GET-then-read-a-shared-backend** (`ClusterAPResolver`, `ClusterDBResolver`, and the AP-version workload GET). Rejected: it is brittle — every future "authorize by a user-credentialed read, then act on a shared backend" endpoint would have to remember to pin — and it makes the authorization GET diverge from the other reads on the same request. Pinning the one `rest.Config` constructor is total, and there is no legitimate reason for *any* user-credentialed read to reach a client-named server.
- **Keep honoring the kubeconfig server but validate it against an allowlist.** Rejected: an allowlist of a single entry is pinning with extra moving parts, and any larger allowlist reintroduces the multi-cluster routing question the platform does not have.
- **Perform the authorization GET through a privileged platform service account** (SSAR or impersonation) instead of the caller's transport. Rejected: the platform deliberately holds no privileged service account for user operations; RBAC must stay bound to the caller's own credentials. Only the transport — server and CA — is platform-owned; identity is not.
- **Override `server`/CA via `clientcmd.ConfigOverrides` instead of rewriting the built `rest.Config`.** Rejected: `mergo`-based override merging will not force `insecure-skip-tls-verify` back to `false` once the client set it `true` (a `false` source is treated as empty), so the one field that most needs neutralizing would silently persist. Overwriting the resolved `rest.Config` fields directly is unambiguous.

## Consequences

- Every user-credentialed apiserver call — telemetry and AP-version authorization, and equally `ap/check-ready`, `ap/versions`, DB access, K8s reads/mutations, logs, and exec — is now sent to the trusted server with TLS verification on; a forged or hostile kubeconfig server is inert. The fake-apiserver bypass is closed for the current endpoints and for future ones in one place.
- Off-cluster/dev runs must set `K8S_API_URL` (and `K8S_API_CA` when the apiserver cert is not publicly trusted) or the API fails closed; in-cluster runs are unaffected. Should F17 (`automountServiceAccountToken: false`) later be applied to the api pod, the in-cluster CA file disappears and the pinned handshake falls back to the default trust store — set `K8S_API_CA` in that case.
- `ResolvedContext.Server` still reports the hostname the caller *declared*. It is informational only — nothing routes on it — and it is no longer the server the request is actually sent to.
- One residual is deliberately left out of scope: a client kubeconfig can still specify **file-path** credentials (`tokenFile`, `client-certificate`/`client-key` paths), which client-go reads from the API pod's own filesystem — a distinct identity-spoofing vector, not a server-trust one. It is inert today because the pod's default service account is unprivileged, but it should be closed by stripping file-based `AuthInfo` from client kubeconfigs so identity, like transport, can only come from inline material. Recorded so this ADR is not read as a claim that the credential path is fully hardened.
