# Pin User-Credentialed Kubernetes Reads to the Trusted API Server

## Status

Accepted for transport pinning. ADR-0048 revises the caller-identity side of this boundary: only the active user's inline bearer token may enter the platform-built `rest.Config`.

The Go API authenticates a caller by its own kubeconfig (`Authorization: Bearer <url-encoded kubeconfig>`) and authorizes every namespace-scoped operation by making the apiserver call **as the caller** and letting Kubernetes RBAC decide. That model is only sound if the apiserver answering is the real cluster. The `rest.Config` used for caller operations is therefore constructed with its **server, CA bundle, and TLS-verification pinned to the platform-trusted apiserver** — first the in-cluster `KUBERNETES_SERVICE_HOST`/`KUBERNETES_SERVICE_PORT` plus the mounted service-account CA, then an explicit `K8S_API_URL`/`K8S_API_CA` fallback for off-cluster development. The client-supplied `server`, `certificate-authority`, and `insecure-skip-tls-verify` are ignored. This is enforced at the single point where every such config is built — `middleware.ResolveContext` and `middleware.RestConfigFromAuth` share `restConfigFromClientcmdConfig` — so no route or service can opt out and no future endpoint can reintroduce the gap. ADR-0048 defines the corresponding identity-input restriction.

This closes the residual that ADR 0045 recorded and left out of scope: a caller could point its kubeconfig at an apiserver it controls that returns fabricated `200`s, satisfy the "GET the target with your credentials" authorization gate for any namespace, and then have the *real* query run against a shared backend under the service's own access — VictoriaMetrics (`VMSELECT_URL`) for workload telemetry, shared Postgres (`DATABASE_URL`) for AP version history. It is the Go-API analog of security-audit finding F5 (the UI's fail-open kubeconfig verification, since fixed by pinning namespace access reviews to the same trusted server) and resolves the audit's cross-cutting "fail-open on server trust" theme for the Go side. Pinning at the source, rather than per endpoint, is deliberate: the only consumer of the kubeconfig's declared server was `ResolvedContext.Server`, which nothing routes on, and the platform is single-cluster with no hub-and-spoke routing — so for a legitimate caller, whose kubeconfig already names the real cluster, pinning is a no-op, and for a hostile one it redirects the read back to the real apiserver, where RBAC denies the cross-tenant access the forged server was meant to fake.

The path is fail-closed. Complete in-cluster coordinates take precedence whenever they are present, so a stale development `K8S_API_URL` cannot move production traffic off the internal control-plane path. If only one of `KUBERNETES_SERVICE_HOST`/`PORT` is present, the request fails as a broken in-cluster configuration rather than silently falling back. When neither in-cluster coordinates nor an explicit `K8S_API_URL` are present, the constructor returns `ErrNoTrustedAPIServer` and the request fails rather than trusting a client-named server. Normal in-cluster deployments need no new configuration because Kubernetes injects the coordinates and mounts the service-account CA. Off-cluster and dev deployments must set `K8S_API_URL` (https only), and `K8S_API_CA` when the apiserver's serving certificate is not chained to the process's default trust store; this mirrors how the UI's F5 fix is scoped.

## Considered Options

- **Pin only the two resolvers that GET-then-read-a-shared-backend** (`ClusterAPResolver`, `ClusterDBResolver`, and the AP-version workload GET). Rejected: it is brittle — every future "authorize by a user-credentialed read, then act on a shared backend" endpoint would have to remember to pin — and it makes the authorization GET diverge from the other reads on the same request. Pinning the one `rest.Config` constructor is total, and there is no legitimate reason for *any* user-credentialed read to reach a client-named server.
- **Keep honoring the kubeconfig server but validate it against an allowlist.** Rejected: an allowlist of a single entry is pinning with extra moving parts, and any larger allowlist reintroduces the multi-cluster routing question the platform does not have.
- **Perform the authorization GET through a privileged platform service account** (SSAR or impersonation) instead of the caller's transport. Rejected: the platform deliberately holds no privileged service account for user operations; RBAC must stay bound to the caller's own credentials. Only the transport — server and CA — is platform-owned; identity is not.
- **Use the complete config returned by `rest.InClusterConfig()`.** Rejected for user operations: besides the internal host and CA, that config contains the Pod service account's bearer token. Replacing the caller-derived config with it would authorize as the workload rather than as the user. Reading the same in-cluster coordinates and CA as trusted transport inputs preserves the useful half without crossing the identity boundary.
- **Override `server`/CA via `clientcmd.ConfigOverrides` instead of assigning trusted transport fields directly.** Rejected: `mergo`-based override merging will not force `insecure-skip-tls-verify` back to `false` once the client set it `true` (a `false` source is treated as empty), so the one field that most needs neutralizing would silently persist. The platform now constructs `rest.Config` from zero values and assigns its trusted transport explicitly, so no client transport field can survive a merge.

## Consequences

- Every user-credentialed apiserver call — telemetry and AP-version authorization, and equally `ap/check-ready`, `ap/versions`, DB access, K8s reads/mutations, logs, and exec — is now sent to the trusted server with TLS verification on; a forged or hostile kubeconfig server is inert. The fake-apiserver bypass is closed for the current endpoints and for future ones in one place.
- Off-cluster/dev runs must set `K8S_API_URL` (and `K8S_API_CA` when the apiserver cert is not publicly trusted) or the API fails closed. In-cluster coordinates always win when present. Should F17 (`automountServiceAccountToken: false`) later be applied to the api pod, the coordinates can remain while the in-cluster CA file disappears and the pinned handshake falls back to the default trust store — set `K8S_API_CA` or mount only the cluster CA in that case; do not restore the service-account token for user operations.
- `ResolvedContext.Server` still reports the hostname the caller *declared*. It is informational only — nothing routes on it — and it is no longer the server the request is actually sent to.
- ADR-0048 closes the credential-path residual by accepting only the active user's inline bearer token and constructing `rest.Config` without clientcmd credential resolution.
