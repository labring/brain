# Authorize Workload Telemetry by Reading the Target Workload

Workload telemetry (the AP and DB CPU/memory/storage/uptime samples behind the canvas footer, served by `POST /api/telemetry/v1alpha1/metrics/{snapshot,series}`) is authorized **per workload, by reading the target workload with the caller's own credentials** — never by trusting that a caller merely holds a parseable kubeconfig. A request is authorized for a target if, and only if, a GET of that target's backing object succeeds under the caller's `rest.Config`: the DB path already had this through `ResolveDBEngine` (a user-credentialed GET of the KubeBlocks Cluster), and the AP path now gets the symmetric gate through `ClusterAPResolver`, which GETs the AP's backing Deployment or StatefulSet the same way `ap/check-ready` and `ap/versions` already do. Kubernetes RBAC — bound to the tenancy namespace — is therefore the authorization decision, matching the platform's kubeconfig-passthrough trust model for every other namespace-scoped read.

The route layer no longer pretends to authorize. `credentialFromAuth` only parses the header and rejects a malformed kubeconfig early (400); it makes no apiserver call and asserts no access. The workload telemetry service is the single authorization point for both target kinds, so a new target kind cannot be added without a resolver deciding access. This closes the prior gap where the telemetry endpoints authenticated a credential (parsed it, built a `rest.Config` locally) but never authorized it against the resource, so any structurally-valid dummy kubeconfig reached the query builder — and, for AP targets, reached it with no Kubernetes call at all, letting the service query VictoriaMetrics under its own `VMSELECT_URL` for any namespace.

A denial is collapsed to a single generic invalid-target result — the endpoint never distinguishes "exists but forbidden" from "does not exist", so it cannot be used as a cross-namespace existence oracle. In a batch snapshot this surfaces as that item's error while sibling targets still resolve (the existing partial-success model); for a single series it is the request error. Both mirror how an unresolvable DB target already behaves.

Separately, telemetry PromQL is never built from unvalidated input. Namespace and resource name are substituted raw into `{namespace=~"…"}` label matchers, so both are validated as RFC1123 labels and rejected before any substitution; the same guard covers the DB queries' `#`/`@` placeholders. With real per-workload authorization in front, this is defense in depth — an authorized request always carries a real (hence valid) Kubernetes identifier — but it independently forecloses `namespace=".*"` (all-namespace disclosure) and matcher-breakout injection (`"` → arbitrary PromQL, including query-of-death).

## Considered Options

- **Keep the per-namespace check at the route edge, but make it call the apiserver.** Rejected: the object a metric describes is the workload, not the namespace; per-namespace access is both a weaker and a different permission than "may read this AP", and it would leave the AP path asymmetric with the DB path, which already gates per workload. Authorizing where the resource is read is the fix for an "authenticate-but-don't-authorize" gap, not authorizing one level up.
- **Use a `SelfSubjectAccessReview` instead of a GET.** Rejected: nothing in the codebase uses SSAR; a user-credentialed GET of the concrete workload is the established idiom (`check-ready`, `versions`, `ResolveDBEngine`), needs no extra RBAC verb, and a successful GET already proves both existence and access.
- **Escape the substituted values instead of rejecting them.** Rejected: escaping for a PromQL label matcher is error-prone and easy to under-specify; rejecting anything that is not an RFC1123 label is total and is exactly the character set a real Kubernetes identifier is drawn from.
- **Return 403 on denial.** Rejected: a forbidden response distinct from not-found is a cross-namespace existence oracle. Collapsing both into one invalid-target result removes the oracle at the cost of a less specific error, which is the right trade for a telemetry read.

## Consequences

A snapshot now issues one RBAC-enforcing GET per AP target, as it already did per DB target; canvas-footer batches are small, so the added apiserver reads are bounded. The service is fail-closed: a `Service` constructed without an `APAuthorizer` denies every AP target rather than serving it.

Two residual weaknesses are deliberately out of scope and left as cross-cutting follow-ups. First, the authorization GET — like the DB path's GET — is issued against the apiserver named in the caller's own kubeconfig, so a caller who points its kubeconfig at a server it controls could still satisfy the gate; pinning telemetry reads (and the DB path) to the in-cluster apiserver is the Go-API analog of the UI's fail-open verification (security audit F5) and should be addressed uniformly, not per endpoint. Second, the namespace label matchers remain unanchored `=~` regexes; with values constrained to RFC1123 labels the only residual is a prefix collision between two real namespaces, which is astronomically unlikely for `ns-<random>` names — anchoring the matchers is a cheap later hardening. Both are recorded so a future reader does not mistake this ADR for a claim that telemetry is fully hardened; it closes the no-op-authorization and PromQL-injection findings (security audit F2), not the shared server-trust theme.
