# Project Canvas Deployment Placeholders

Project Canvas should show a lightweight deployment projection for an active Deployment Task once the task has resolved its target Project. Unknown result shape is shown as one generic Deployment Placeholder Node; known result shape is shown as a Deployment Result Preview with one or more Deployment Result Placeholder Nodes and Deployment Preview Edges. These projections are task projections, not pending AP, DB, AP Public Access Node, template workload, or Canvas Connection state, so their identity and temporary positions belong to deployment task projection state rather than durable Canvas Layout.

Deployment projection nodes appear as skeletons, do not create Canvas Connections or expose resource actions, and disappear on failure or cancellation. On success, they remain only until resulting resource nodes appear or a short reconciliation window expires; when a Deployment Result has no existing Canvas Layout position, it inherits the corresponding deployment projection position and that projection node disappears.

Initial placement is chosen by the Project Canvas that first projects an unplaced placeholder, using the same deterministic global placement order as other unanchored canvas nodes unless the deployment has an explicit resource anchor; existing canvas selection and current viewport are not anchors. The first recorded placement wins until a user intentionally moves the placeholder. Visible placeholders participate in placement occupancy, and the current viewport may move to the newly projected placeholder as a session-local follow behavior, but handoff does not override an existing Canvas Layout position for a resulting resource.

When a Deployment Result Preview becomes available, it replaces the generic Deployment Placeholder Node for that Deployment Task rather than appearing alongside it. The preview may include AP, DB, AP Public Access, or template-native result placeholders only when the task has enough evidence to describe them; uncertain results stay represented by the generic placeholder. Each preview placeholder is keyed by a task-local Deployment Result Slot and may carry an expected result identity for handoff, but it does not use Canvas Resource Identity before the real resource exists.

Deployment Preview Edges are drawn only from explicit preview evidence, such as generated AP-to-DB reference intent, a template-declared dependency, or the AP-to-Public-Access presentation relationship. Producing multiple results from the same Deployment Task groups them for placement and handoff, but it does not by itself create an edge.

Deployment Result Preview is derived only from structured evidence: generated Brain manifests or YAML, `artifactSummary.resources`, direct deployment settings rendered into manifests, template-provider previews, AP public access intent, and AP-to-DB reference evidence. Natural-language prompts, broad task source type, or UI flow labels are not enough to create preview result slots or preview edges; earlier previews require an explicit structured `expectedResults` contract.

Deployment Result Preview Placement is chosen for the preview group as one combined footprint and then expanded into per-slot positions. When handoff occurs from a known preview group, each resulting resource inherits its matching slot position if it has no existing Canvas Layout position. When handoff occurs from an unknown generic placeholder, only the Primary Deployment Result inherits the placeholder position.

Deployment Handoff may complete per result slot. If one previewed resource appears before another, the appeared resource may replace its matching Deployment Result Placeholder Node while unresolved result slots remain visible. Temporary preview edges may continue to connect handed-off resources and unresolved result placeholders, but they remain distinct from Canvas Connections until saved resource state provides real connection evidence.

Deployment Result Placeholder Nodes are not shown for expected results that already have live canvas nodes or saved Canvas Layout positions. Existing resources remain at their saved positions and may act as placement anchors for new result placeholders; showing update badges or task status on existing resources is a separate concern.

When an unknown generic placeholder upgrades into a known Deployment Result Preview, the existing generic placeholder position anchors the preview's primary slot. If the expanded preview group would overlap existing canvas occupancy and the generic placeholder has not been intentionally moved by a user, the Project Canvas may choose a new deterministic global position for the whole preview group. If the generic placeholder has been intentionally moved by a user, the preview should preserve the primary slot at that user-chosen position and place secondary slots in the nearest non-overlapping anchor-local positions.

Deployment projection positions record whether they were generated by Project Canvas placement or chosen by a user move. Generated positions may be recalculated when a generic placeholder upgrades into a more precise Deployment Result Preview; user-chosen primary positions remain authoritative for that Deployment Task projection until the user moves them again or handoff completes.

Deployment projection state remains on the Deployment Task Projection rather than Canvas Layout or a separate canvas table. The projection keeps a generic placeholder position for unknown result shape and may add task-local result slots and preview edges for known result shape; slot positions are projection positions used for handoff, not durable resource layout rows.

Dragging a Deployment Result Placeholder Node moves the whole Deployment Result Preview group by default. Per-slot manual placement is out of scope for the initial interaction model because it would let one Deployment Task's anticipated results drift apart before handoff.

Viewport follow remains session-local. Unknown generic placeholders may be followed as a single node; known Deployment Result Previews should fit the preview group so the user sees the anticipated result shape without changing projection placement.

Handoff uses the Deployment Task's declared result resources, such as `artifactSummary.resources`, and preview evidence such as generated manifests, rather than naming conventions or creation time. When a resulting resource appears before the matching deployment projection position has been recorded, the Project Canvas should preserve the deployment projection path instead of letting the resulting resource independently choose a first placement; in that race, the result may be withheld from canvas placement until its preview slot position is recorded. The first implementation includes task-list projection, skeleton rendering, temporary position persistence, successful handoff, and automatic disappearance for failed, cancelled, or expired completed tasks; task detail panes, failure nodes, detailed status cards, and existing-resource update badges are out of scope.

## Considered Options

- Model deployment progress as pending resource nodes: rejected because task start does not reliably know the final resource type, name, or count, and pending resource identities would blur the boundary between Deployment Tasks and saved AP/DB/resource state.
- Persist placeholders in Canvas Layout: rejected because Canvas Layout is durable Project resource arrangement, while deployment placeholders are temporary task projections.
- Hide the placeholder immediately when a task completes: rejected because task completion and resource-list reconciliation can be briefly out of sync, producing a visible gap before the real node appears.
- Place unanchored placeholders near the current viewport: rejected because placeholder placement is project-scoped task projection state, while viewport position is session-local. The viewport may follow the deterministic placeholder position without defining it.
- Show a generic task placeholder alongside known result placeholders: rejected because one Deployment Task should have one canvas projection shape at a time, and parallel generic/result projections make the task appear to produce extra resources.
